多代理开发通用提速方案（保证质量前提下）

一、适用前提
- 有一个主会话做总控，只调度、不亲自写代码；实现、审查、调研都交给子代理。
- 任务按批次推进，每批有设计文档和测试合同（要验证的场景、预期结果）。
- 子代理不能再派子代理，所有派活都从主会话发出。

二、先找慢在哪
1. 整条链串行：调研 → 实现 → 审查 → 修复 → 复核，后一步干等前一步。
2. 单个执行者从头做到尾，多个步骤排成一条线。
3. 子代理每次都从零读上下文，同样的东西重复读好几遍。
4. 测试慢：每条用例都要搭真实环境。
5. 子代理没拿到结果就提前返回，白绕一轮。
6. 主会话在子代理干活时空等。

三、提速做法
1. 跨批流水线
   - 当前批在审查或修复时，派只读子代理预先调研下一批：核对设计、列出和现有代码的冲突、拆解测试合同、写出实现计划。
   - 下一批开工时直接拿这份材料派活，省掉重复调研。
   - 规则：预调研只读、不改文件；下一批的实现要等上一批提交后才开始。

2. 测试先行并行
   - 同一批里，测试子代理按测试合同写用例，实现子代理同时改业务代码。
   - 两边改的文件不重叠（例如一边只改测试文件，一边只改服务层）。
   - 测试子代理只按合同定断言，不参考实现代码。这样测试是一份独立的标准，比实现写完再补测试更严。

3. 多路并行审查
   - 中及以上难度的批次，同时派 2–3 个互相独立的审查者，各盯一个方面：
     a. 状态机、写入门禁、失败路径（状态是否被改坏、能否被绕过）；
     b. 测试合同覆盖、断言是否真实（不只看返回 0）、前置条件是否用真实命令造出；
     c. 同步、生成物、文档回填、是否超出本批范围。
   - 结论取最严的一路；必须修的项合并成一份清单交给修复者。

4. 定点复核
   - 修完必须修项后，新开一个审查者，只核对这些项和对应的反例测试，不重审整批。
   - 审查者一律新开会话，不传执行方的会话 ID，不把执行方的结论当证据，必须自己读代码和 diff。

5. 测试分片
   - 先核实测试工具的临时目录互相隔离：各用唯一目录、不写共享文件、用例之间不互相依赖。
   - 核实通过后，把定向用例按组拆开，多进程并行跑，每组各用一个报告目录。
   - 有隐式依赖的用例放进同一组。

6. 杜绝提前返回
   - 派活时写明：测试在前台运行、不设超时，拿到报告和退出码才能返回。
   - 固定回报格式：改动文件清单、关键决定、命令与退出码、报告路径、延期项、需要用户拍板的问题。
   - 回报里只有「等待中」的，主会话立刻让同一个子代理接着做完，不重开新会话。

7. 主会话不空等
   - 长任务放后台；等待时去派互不冲突的只读调研或核实任务。
   - 主会话只看短结果，详细内容写在报告文件里，避免主会话上下文膨胀。

四、并行的边界（不能为提速破坏）
- 同一时间只允许一个子代理改同一个文件；会改同一文件的步骤必须串行。
- 有因果依赖的批次不并行实现；用 worktree 并行开发只适用于真正互不依赖、文件不重叠的部分。
- 审查必须在实现之后，复核必须在修复之后，这两步不能省。
- 测试分级不变：小改只跑相关定向测试；阶段收口跑本阶段的定向合集；全量测试只在全部完成时，或改了共用核心、定向测试覆盖不到时才跑。
- 失败保持失败：不删断言、不降级、不用默认值过门禁。

五、模型分配（按难度，能用低档完成就不升档）
- 低/中低（查找、核对、读设计）：轻量模型，中低强度，只读。
- 中（小改一处、写测试）：轻量模型高强度执行，强模型审查。
- 高（多文件、改控制逻辑）：强模型高强度执行，强模型更高强度审查。
- 极高（状态机、写入门禁）：强模型最高执行强度，强模型最高审查强度，多路审查。
- 做失败或结果不可用才升一档。

六、单批标准节奏
1. 上一批审查或修复期间：预调研本批（只读）。
2. 开工：测试子代理和实现子代理同时派出。
3. 实现完成后先跑定向测试（可分片），再派 2–3 路并行审查。
4. 修复者处理必须修项 → 定点复核。
5. 通过后按显式路径暂存、本地提交；回填进度；同时派出下一批的预调研。

七、预期效果
- 单批耗时大约降到原来的一半，主要来自三处：预调研把等待时间用起来，测试和实现并行，审查从串行改成并行。
- 质量不降反升：测试是独立写的标准，多路审查覆盖面更宽，定点复核不放过必须修的项。
