# 完整调研和制定方案

走完整调研和制定方案时读这一份。紧要调研要重做模型核验时，只读「模型核验」一节；判断主控是否合格时，只读「主控模型」一节。

目录：

- 完整调研
- 模型核验
- 主控模型
- 制定方案

## 完整调研

这一阶段只产生事实，不写方案，不探测执行模型，不派开发任务。

1. 问用户这台电脑上有哪些 agent 工具、哪些模型。不要自己先查目录、进程或配置。告诉用户可以直接发截图。用户给了名单或截图，只按用户给的内容继续，缺的再问。用户说不知道，再自己查，查完给用户确认后才用。
2. 扫磁盘，列出可用空间，为工作目录做准备。Windows 用 `Get-PSDrive -PSProvider FileSystem`。这一步不依赖名单，可以和第 1 步同时进行。
3. 名单确认后，同时做两件事。联动只认两件：能不能把任务派给对方，对方的结果能不能交回来。看不出来就标成无法检查并问用户，不猜。不能联动的不要当成可以调度的子代理。另一件是当前工具能不能调用不同供应商的模型。看不出来先再问一次。仍然看不出，或确认不能：停在这里，回复「此技能适用于 OpenCode，可以转向 OpenCode 使用。」OpenCode 能调多个供应商时，这一项通过。
4. 按「模型核验」核验用户给的每个模型，列出能力档次、上下文、是否支持工具调用、价格和来源。价格以用户给的为准，不清楚就问，不猜。
5. 按「主控模型」选主控。

工作目录推荐可用空间最大、且不是系统盘的那个盘，建 `tiaokong-work`。不假设任何盘符或旧目录。脚本只从本机配置或 `TIAOKONG_WORKROOT` 取路径，没配就问。宿主工具、主控模型、工作目录写入本机配置。用户选定后才写。

## 模型核验

什么时候做：完整调研时每次都做；紧要调研时，方案用到的模型在模型记录里的核验日期超过 30 天，只对这几个再做；用户说「重新核验」时。

来源分三级：

| 级别 | 来源 | 用法 |
|---|---|---|
| 一手 | 模型厂商的官方文档、模型卡、价格页、发布说明 | 结论以它为准 |
| 二手 | 本机配置「可信来源」里的来源；或者满足下面四条的机构、网站、社区发布的评测、榜单、汇总（包括 AI 生成的汇总） | 只作参考，写明出处，只补一手没写的部分。和一手冲突时以一手为准 |
| 不采用 | 不满足四条的：聊天机器人的回答、匿名的 AI 汇总、内容农场、个人博客和自媒体、转卖商自己的宣传 | 不写进记录 |

不在「可信来源」里的，四条都满足才算二手：发布方明确，是机构、正规网站或成规模的社区，不是匿名账号；方法公开，写明怎么评测、数据从哪来；结论可追溯，能找到原始数据或原文；持续维护，有更新日期。例如 SWE-bench 官方榜、LMArena、Stanford HELM 一般满足，这是例子，不是名单。拿不准的按不采用处理，在报告里列出来，问用户要不要加进「可信来源」。

每条结论写来源链接和核验日期。几个来源说法不一致，把冲突原样列出来，不替用户挑。查不到一手资料，写「未查到官方资料」，不拿二手或不采用的来源顶替，不凭记忆补。

中转供应商给的模型名，不能证明实际调用的就是那个模型。所以分两步：完整调研时只联网查官方资料，不探测；本地探测留到制定方案选定执行模型之后，按 `SKILL.md`「探测」一节做，结果补进模型记录的「探测结果」一列。探测回复里自称的模型和方案写的对不上，写进报告请用户判断，不自己下结论。中转价和官方价不同时两个都写，标明哪个是用户给的。

当前会话没有联网工具，这一项标成「无法检查」，问用户能不能开联网，或者由用户提供资料。

结果按 `SKILL.md`「模型记录」一节写进模型记录的「核验」一节。方案只写用哪些模型，不抄能力数据。

## 主控模型

主控要满足三条，依据是核验到的一手资料：

- 官方资料写明支持工具调用，能做多步的代理任务。
- 上下文放得下 `SKILL.md`、档案和方案的启用要点、多轮汇报和子代理的短结果，建议不少于 128K。
- 在用户给的模型里，推理和规划属于最强的一档。

当前会话的模型满足就推荐它；不满足，推荐满足条件里最强的一个。没有一个满足：如实告诉用户「你给的模型里没有能担当主控的」，列出每个模型差在哪一条、依据的来源。不硬选，不夸大能力，不编造没核验到的信息。然后问用户：换一个模型做主控；或者不用本 skill 调度，只用 `rules/` 下的两份文件。用户没选之前，不进入制定方案。

## 制定方案

完整调研没结束，不能进入。这一阶段不重新问工具和模型。

先选方向，再选执行模型，再探测，最后写文件。四个方向的说明可以同时起草。用户没选定之前，不探测，不写最终方案文件。

只列出这台电脑上做得到的方向。优劣只点名完整调研里确认过的模型，不拿 `references/presets/` 做比较，也不读那些文件。

价格相同、能力不同的模型，例如同一供应商同价的两档模型，不按名字拆成省钱和高效，也不替用户挑。放在同一个方向里问用户用哪一个，说明能力差在哪、价格一样。只有价格不同，才按价格和能力分出省钱、高效、均衡。

| 方向 | 什么时候给 | 怎么讲 |
|---|---|---|
| 省钱 | 有更便宜或更低档的模型 | 用哪些模型、档位多低、省在哪、慢在哪、不适合什么任务 |
| 高效 | 有更强的模型，额度允许更高档或更多并发 | 用哪些模型、快在哪、额度为什么更容易用完 |
| 均衡 | 至少有一强一弱两种模型 | 难任务和审查用哪个，机械任务用哪个。默认推荐这个方向 |
| 沙盒 | 有能在外部单独执行、并且和 OpenCode 对得上联动的工具 | 真实目录更安全，但多了拷贝和核对。没有这种工具就写明不提供 |

做得到的方向按省钱、高效、均衡、沙盒排列。默认推荐均衡。没有均衡时，推荐这个序列里第一个做得到的。

四个方向都做不到时，如实告诉用户原因，例如只有一个执行模型、又没有沙盒工具。然后问用户：是否只用 `rules/subagent-rules.md` 和 `rules/review-standard.md`，不用本 skill 调度。用户要用，就告诉他在项目规则里写一句「遵守 <路径>」，本 skill 到此结束，不写方案。用户都不用，就结束本 skill，不写方案、不改本机配置、不改项目档案，保留原有状态。

用户选定方向和执行模型后，按 `SKILL.md`「探测」一节逐个探测这些即将写入的执行模型。没通过就不写文件，汇报原因，让用户换模型或换方向。全部通过后，只按这个方向写一份方案，写入这个项目的方案目录。

文件名用方向的英文名：`saving.md`、`fast.md`、`balanced.md`、`sandbox.md`。同一个方向已有文件时，加数字后缀，依次为 `balanced-2.md`、`balanced-3.md`，不覆盖旧文件。用户自己起了名字就用用户的，重名时先问。

方案按 `SKILL.md`「启用要点」一节的结构写：`## 启用要点` 里写在哪里执行、用哪些执行模型（价格相同的几个里选了哪一个）、档位表、额度用完或限流时怎么办；沙盒方向的长步骤放在 `## 沙盒步骤`。缺档位表，这一阶段不算结束。

沙盒方向还要写上最短步骤：工作目录取自本机配置，用 `scripts/` 里的通用脚本建沙盒、派出、核对、拷回、清理。执行工具的命令和参数写在方案的执行工具表里。有适配目录的（如 `scripts/adapters/agy/`）按它的 `README.md` 加步骤。缺这些步骤，也不算结束。不读旧例子，不把旧例子里的模型 ID 抄进去。

改方案之前先备份。没备份就不改。备份只含这个项目的方案，放在该项目的档案里写明的备份路径，不含 `.git`。不备份别的项目。

只在用户明确要求时新增、删除或还原方案，只作用于当前项目的方案目录。还原前再问一次。不推送。用户另说「还原规则」，由维护会话用 git 还原规则文件，不从项目备份还原。不删除、不改写 `references/presets/` 和 `scripts/`。
