# 维护时的验证

维护 skill 本体时用。按改动类型定跑什么，能用静态核对确认的，就不运行脚本。

| 改了什么 | 跑什么 |
|---|---|
| 只改规则文字 | `docs/tools/check-paths.ps1`（路径都存在、编码正确）；派一路只读审查，查前后矛盾 |
| 改文件名或路径 | 上面这些，再搜旧名字有没有残留引用 |
| 改脚本里会执行的代码 | 先静态核对：语法解析、读一遍改动、确认改到的路径和参数存在。确实只有实际运行才能确认时，才跑冒烟，而且先告诉用户为什么要跑、跑什么、要多久，用户同意再跑 |
| 改脚本逻辑 | 派子代理在沙盒实测，限时；同一条失败两次就停下写报告。也要先问用户 |

- 只改注释，或者只改了文档里怎么写脚本的名字，不算改了会执行的代码，不跑冒烟。
- 子代理测试一律限时。同一条失败两次就停下写报告，不无限重试。
- 审查报告写在仓库外的维护目录，不放进仓库。

## 编码

- Markdown：UTF-8 无 BOM，LF。
- `.ps1`：UTF-8 带 BOM（Windows PowerShell 5.1 读不带 BOM 的脚本会把中文读坏）。

## docs 的用法

- `docs/` 只用于维护 skill 本体，启用 skill 时不读。
- `docs/` 入库，会公开在 GitHub 上。这里只放通用内容，不写盘符、用户名、具体供应商和模型。
- `docs/plans/`：进行中的优化方案。审查确认、合入之后，移进 `docs/archive/plans/`。
- `docs/archive/`：不入库，只在本地。
- `docs/basis/`：用户的原始规则原文。改规则时和 `SKILL.md` 一起改，避免两套口径。
- `docs/path-map.md`：2.3.0 的路径对照。
