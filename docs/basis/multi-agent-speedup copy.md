# 多代理开发协作与提速规则

## 一、目标与职责

在不降低既定验收标准、不突破授权范围的前提下，减少等待、重复读取和无效返工。

- 主会话担任总控，负责规划、拆分、派单、协调、证据核对和进度维护，不直接编写业务代码。
- 调研、实现、测试编写、修复和独立审查交给子代理。
- 子代理不得再派子代理，所有调度均由总控发出。
- 总控可以运行验证、执行只读检查，并在授权范围内管理 Git。
- 优先复用项目已有设计、测试合同和规则，不为小任务重复编写成套文档。
- 提速依靠有效并行，不以代理数量或报告数量作为成果。

## 二、每批开工前

总控明确以下内容，简单批次可直接写入派单，不强制另建文档：

1. 本批目标和完成条件。
2. 依据的需求、设计及测试合同。
3. 允许修改的文件、禁止触碰的范围。
4. 子任务的依赖关系、接口约定和共享资源。
5. 执行模型、档位、验证方式及报告位置。

派单只包含本批所需的信息和必要文件路径，不重复粘贴整套项目规则。

只有满足以下条件才拆分并行：

- 各任务有清晰、可独立验证的产出。
- 同时修改的文件不重叠。
- 不存在未解决的因果、数据或资源依赖。
- 拆分收益明显大于启动、读取上下文和结果整合的成本。

判断不清时串行，不为凑并发硬拆任务。

## 三、跨批流水线

当前批进入审查或修复后，可以派只读子代理预调研下一批：

- 核对需求和现有实现。
- 找出设计冲突、依赖和风险。
- 整理测试场景及实施建议。

边界：

- 预调研不得修改业务文件。
- 下一批实现必须等待上一批通过并提交。
- 下一批开工前，总控依据上一批提交后的代码复核预调研结论；受影响的部分必须更新，不能直接使用过期材料。
- 没有明确收益的预调研不派发。

## 四、同批执行与审查

### 1. 测试与实现

接口和测试合同已明确、文件互不重叠时，可以同时派出：

- 测试作者：按需求和测试合同编写用例。
- 实现者：按同一约定编写业务实现。

测试作者可以读取公共接口、现有测试和必要夹具，但不得照着本批新增实现反向修改预期结果。

约定不清时，先明确约定，再并行。约定发生变化时，总控统一更新，并要求受影响任务重新核对。

简单任务不强制拆成两个代理，可由一个代理先写测试、确认有效，再实现。

### 2. 独立审查

实现完成、代码稳定并取得定向测试结果后，再开始审查。

按风险安排审查：

- 简单、低风险改动：主控机械核对，必要时增加一路独立审查。
- 常规实现：安排独立审查，存在多个独立风险面时再增加审查者。
- 高风险或跨模块改动：安排 2–3 路独立审查，分别关注：
  a. 正确性、状态流转、并发、安全及失败路径；
  b. 测试覆盖、断言有效性、真实前置条件和运行证据；
  c. 模块衔接、生成物、文档同步及范围越界。

审查者使用新会话，不复用实现者的会话；必须自行核对需求、代码、diff 和必要证据。

总控按证据和影响合并问题，不按人数投票，也不因某一路措辞更严就直接采纳。争议必须核实。

### 3. 修复与复核

- 将必须修复的问题合成一份清单，明确责任人。
- 可选优化不自动扩大为本批任务。
- 修复完成后，由独立复核者核对修复项及对应反例。
- 未受影响的部分不重复全量审查。
- 修复扩大了范围或改变公共约定时，扩大相应审查与测试范围。
- 未关闭的必须修项，不得进入提交。

## 五、测试和任务运行

### 测试范围

- 小改：运行相关定向测试。
- 阶段收口：运行本阶段相关测试合集。
- 最终交付，或公共核心变更无法被定向测试充分覆盖时：运行全量测试。
- 不为追求速度降低原有验收标准。

### 测试分片

并行运行前，确认各组：

- 使用独立临时目录和报告目录。
- 不争用端口、数据库、共享文件或其他资源。
- 不依赖其他组的运行顺序和结果。

存在依赖的用例同组串行；无法确认隔离时不分片。

### 任务生命周期

- 命令设置合理超时，记录实际退出码和结果。
- 同步任务取得最终结果后返回；正式后台任务保留任务标识，按工具通知接收完成结果。
- 不把“已启动”“等待中”当成任务完成。
- 异常提前返回时，优先续接原子代理，不重复启动同一任务。
- 超时或失败时，只处理本任务创建的进程与临时资源。

失败保持失败：不得删除断言、跳过必要场景、伪造前置条件或使用默认值绕过门禁。

## 六、模型与等待时间

- 只使用用户或项目方案允许的模型和档位，不猜测模型 ID、能力或可用档位。
- 机械核对和范围明确的任务优先使用成本较低、能力足够的模型。
- 跨模块、复杂控制逻辑及高风险任务使用具备相应能力的模型。
- 审查者必须具备识别相应风险的能力；高风险任务不能仅为省钱降低审查能力。
- 失败后先区分需求、派单、环境、接口和模型能力问题；只有能力不足才考虑升档。
- 升档、换模型及增加成本遵守项目授权，不自动突破预算。
- 同一问题连续两轮无法解决时，停下报告原因与可选方案。

长任务可以放后台。等待时只安排确有价值、互不冲突的任务；没有合适任务就正常等待，不制造额外工作。

## 七、回报、提交与日志

### 子代理回报

保持简短，包含：

- 结果：完成、失败或阻塞。
- 修改文件及必要的关键决定。
- 实际运行的命令、退出码和验证结论。
- 未执行项、遗留问题及证据位置。

详细证据按项目约定保存；不向主会话重复粘贴整份日志。简单任务不强制另写长报告。

### 单批收口

总控核对：

1. 改动未超出授权范围，未覆盖用户已有修改。
2. 对应测试和审查有实际证据，必须修项已关闭。
3. 没有本批遗留的运行任务或临时资源。
4. 在已获提交授权时，只暂存明确属于本批的文件并提交。
5. 更新进度，再启动下一批实现。

不得使用 `git add .` 混入无关改动；不擅自推送、重置或丢弃用户修改。

### 项目进度日志

- 新记录置顶，只保留最新五条。
- 每条尽量一行：

  日期｜当前阶段｜本次结果｜验证情况｜下一步或阻塞

- 不记录重复分析和派单全过程。
- 长期有效的决定写入方案或规则，不能只留在短日志中。
- 未解决的阻塞不能因旧记录被移除而视为已解决。
- 五条限制针对进度摘要，不据此删除原始测试或审查证据。

## 八、效果判断

以实际耗时、等待时间、返工和缺陷情况判断是否提速；没有对照数据时，不承诺“耗时减半”“成本更低”或“质量必然提升”。

任何提速措施不得替代必要验证，也不得把未验证结果描述为已通过。
