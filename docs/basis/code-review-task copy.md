# 代码审查任务

只读审查，不修改代码、不提交；只运行已获授权的检查。

## 审查依据
- 差异范围：<git diff 比较范围，或文件列表＋比较基线>
- 需求/方案：<文档路径或本次目标>
- 项目规则：<适用规则路径>

比较基线或目标不明确时，先询问，不自行猜测。
范围外代码只用于核对调用链、输入约束和已有防护，不报告原本就存在的问题。

## 问题成立条件
只报告本次改动新引入或明确加重的问题，并确认：
1. 触发输入或操作在实际调用路径中可达。
2. 现有校验、异常处理或调用约定没有阻止该问题。
3. 能指出具体代码及其导致错误的过程。

静态代码证据可以支持结论，不强求所有问题都实际复现；
但不得把推演、未执行的测试写成“已复现”或“验证通过”。

## 问题分级
- 阻断：导致严重错误行为、数据丢失或损坏、权限绕过、关键路径崩溃，或破坏现有调用契约。
- 应修：有明确触发条件和实际后果的功能或边界缺陷，如空值处理错误、重复提交、分页遗漏、并发覆盖、资源泄漏。

按实际后果定级，不因涉及“并发”“安全”等关键词直接升为阻断。

## 不报告
- 命名、格式、注释和风格偏好；涉及项目明确强制条款时，必须引用条款。
- 与本次目标无关的重构、更好的写法、性能微优化。
- 单纯“缺少测试”，但不能指出具体错误路径的问题。
- 方案已明确接受的取舍；但确证的越权或数据损坏问题仍须报告。
- 没有可达触发路径的猜测，或已被其他代码防护的问题。

## 每条问题的格式
- [阻断/应修] 简短标题
- 位置：文件:行号，默认使用新版本行号；删除代码注明旧版本。
- 触发条件：具体输入、操作或执行顺序。
- 后果：用户、调用方或数据层面的实际影响。
- 证据：相关代码及完整因果链；注明静态判断或实际复现。
- 修复建议：一句话，优先给出符合现有方案的最小修复。

同一根因合并报告，不按多个表现重复列项。

## 待核对
只有缺少某项具体事实，且该事实会影响审查结论时才列入。
写清：缺少什么、为何重要、如何核对。
不要把无法成立的猜测转移到这里凑数，最多3条。

## 输出
1. 结论：
   - 可合并：本次范围未发现阻断或应修问题，且无影响结论的关键待核对项。
   - 修复后可合并：存在应修问题，无阻断问题。
   - 不可合并：存在已证实的阻断问题。
   - 暂无法判断：范围、依据或关键事实不足，无法完成有效审查。
2. 阻断问题。
3. 应修问题，按严重度排序，通常不超过5条；确证更多时不得为限额隐去。
4. 待核对。
5. 检查说明：实际运行了什么、哪些未运行，简短列明。
