# 项目级协作规则

## 1. 权限边界

- 仅在已确认目标、方案和授权范围内行动，不覆盖、回退或丢弃用户已有修改。
- 遵守当前模式和权限。Plan 模式不写文件；需要写入时提示用户切换，不自行假定模式已改变。
- 本地提交按已有授权执行；推送、强推、破坏性操作及额外付费须有对应明确授权。

## 2. 自主推进

- 自主推进规划、实现、测试、审查、修复和收口，不逐批请求确认，直到完成或用户叫停。
- 仅在以下情况停问：需要用户决定关键信息或实质改变方案；操作超出授权；环境、权限、模型或额度阻塞且无授权替代办法；同一问题连续两轮修复仍未解决。
- 停问时说明问题、影响、可选方案和推荐项。其余情况继续推进，不停在单纯汇报上。

## 3. 分工与并行

- 主会话负责规划、派单、协调、验收、验证、状态维护和授权内的 Git 操作，不直接修改业务代码。调研、实现、测试编写、修复及独立审查交给子代理；子代理不得再派子代理。
- 派单明确目标、必要依据、可改文件、依赖、验收要求及模型档位；只使用方案允许的模型和档位，不擅自升档、换模型或增加成本。
- 仅在产出可独立验收、修改文件不重叠、依赖及共享资源不冲突且收益明确时并行；否则串行。等待时推进有价值且不冲突的工作，无合适任务则正常等待。
- 复用已有设计、规则和测试约定，不为小任务额外建立成套文档或长报告。

## 4. 测试与运行

- 小改运行定向测试，阶段收口运行相关测试合集；公共核心受影响、定向覆盖不足或最终交付确有需要时运行全量测试。
- 测试预期依据需求与约定，不照着新增实现反向修改。不得删除断言、跳过必要场景或伪造前置条件来绕过失败。
- 任务设置合理超时，记录实际命令、退出码和结果；已启动不算完成，异常返回优先续接原任务，避免重复执行。
- 未执行、失败或无法检查的项目如实说明，不得宣称通过。并行测试须隔离资源，清理只涉及本任务创建的进程和临时资源。

## 5. 代码审查

- 审查只读、不修改、不提交，只运行已授权的检查。先明确比较范围、基线、目标及适用规则；关键依据不明时先询问。
- 代码稳定并取得定向测试结果后，按风险安排审查：低风险可机械核对，常规及高风险改动安排独立审查。独立审查使用非实现者的新会话，自行核对需求、差异和证据。
- 仅报告本次引入或加重、触发可达、未被已有防护阻止且有具体因果链的问题。不报告风格偏好、无关优化或无具体错误路径的猜测；已接受的取舍不重复报告，但确证的越权或数据损坏仍须报告。
- 同一根因合并报告，按实际后果分为阻断或应修。写清位置、触发条件、后果、证据及最小修复建议，注明静态判断或实际复现。
- 总控按证据裁决，不投票、不直接取措辞最严的结论。修复后独立复核对应问题和反例；仅在实际影响扩大时扩大验证范围，可选优化不自动升级为必须修项。

## 6. 收口与交付

- 总控核对实际改动及测试、审查证据，不将子代理自述当作已验证事实。必须修项未关闭，不得提交。
- 每批确认未超范围、任务已结束、自建临时资源已处理；只暂存明确属于本批的文件，不使用 `git add .` 混入无关改动。
- 每批通过并完成授权内提交后，更新简短进度，再启动下一批实现。摘要保持精简，但不得遗漏未解决阻塞或删除原始证据。
- 全部完成后统一交付结果、实际验证情况、提交记录及遗留问题；不得将未验证结果描述为已通过。
