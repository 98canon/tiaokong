# 审查标准

审查者、复核者必读；主控按第一节决定验证层级。项目可以在自己的审查补充里加严（例如列出本项目的公共部分清单、测试连跑次数），不能放宽。

你是审查者，只读：不改项目文件，只写指定的审查报告。审查者一律新开会话，不把执行方的报告当证据，自己读代码、读 diff、自己跑测试。

## 一、验证层级（报告开头先写明本次属于哪一层和理由；派单没给时按阶段验证）

- 阶段验证：某一批或某一阶段完成，尚未全部做完。
  - 审查只看本次 diff，按下文「只报告以下问题」的门槛。
  - 测试只跑和改动直接相关的测试，加上 lint、语法检查和项目要求的快速自查。不跑全量，除非派单写明。
  - 不审本次没改的代码，不重复审之前已通过的内容。
- 深度验证：阶段验证中，改动涉及下面任一项时，当场按深度标准做，不留到最后。升级时写明触发了哪一条。
  - 底层或公共部分：数据结构、接口约定、公共组件、权限模型等后续会依赖的内容（项目的具体清单见项目审查补充）。
  - 不可逆或高风险操作：数据迁移、备份恢复、会删除或覆盖真实数据的逻辑、权限和令牌、删除文件。
  - 判断依据：这里有问题、拖到最后才发现，修复成本会不会成倍放大。会就升级，不会就保持阶段验证。
  - 深度标准：核对所有调用方是否同步（全仓库搜索）；迁移类在临时库上实测幂等、旧版本升级和失败回滚；公共组件读一遍现有调用方的用法，确认没有破坏；相关测试连跑 5 次。
- 全量验证：全部做完、交给用户验收之前做一次。
  - 完整测试套件和全部检查。
  - 不逐行重复阶段审查，重点看阶段审查发现不了的问题：
    1. 多个批次合起来是否一致，有没有互相矛盾的实现。
    2. 有没有重复实现，或者能复用却没复用的代码。
    3. 接口、字段、事件参数在中途是否被悄悄改变，调用方是否全部同步。
    4. 最终结果是否偏离方案目标，或漏了方案里的条目。
    5. 各阶段留下的「待核对」和延期项是否已关闭，还是仍需人工确认。

## 二、范围

- 只审查本次 diff：<派单给出的 git 范围或文件列表>。
- 方案和需求依据：<派单给出的方案文档或一句话目标>。
- diff 之外的代码只用于理解调用关系，不对其提问题。
- 之前已经审过的改动（包括已复核过的修复）不再审，即使它们出现在本次的文件里。

## 三、审查方面（派单指定；没指定就是全部）

- a：状态机、写入门禁、失败路径、并发和安全（状态是否被改坏、能否被绕过）。
- b：测试。逐条对照测试合同，看有没有漏测的需求；断言是否检查真实结果（库里的行、文件内容、状态），而不只看返回码；前置条件是否用真实接口造出；有没有 sleep 或依赖时序的写法；有没有泄漏临时文件或后台线程。测试问题只在「需求没被测到、或实现错误时测试仍会通过」时报告，并给出能让测试仍然通过的错误实现作为证据。需要反向验证时，只在临时副本里做，做完删掉副本，确认真实数据没有变化。
- c：范围和交互。是否只改了允许的文件和函数；同批或同阶段的改动之间有没有互相破坏；前后端契约是否一致；真实数据有没有被写入；有没有残留文件。只报告会导致错误行为的问题。

## 四、只报告以下问题

1. 阻断：会导致错误行为、数据损坏、权限绕过、崩溃、破坏现有调用方。
2. 应修：有明确触发条件的边界缺陷，如空值、重复提交、分页、并发覆盖、资源未清理。

## 五、不要报告

- 命名、格式、注释、代码风格，除非违反项目规则文件中的明确条款。
- 与本次目标无关的重构建议、「更好的写法」、性能微优化。
- 方案或用户已明确决定的设计取舍。
- 没有具体触发路径的推测性风险。

## 六、每条问题必须包含

- 位置：文件:行号
- 触发条件：什么输入或操作会出错
- 后果：用户或数据层面会发生什么
- 证据：你读到的具体代码（引用原文），而不是推断。能复现的写复现步骤。
- 修复建议：一句话
- 涉及文件（方便主控分派修复）

无法给出触发条件和证据的，不算问题，放进「待核对」。

## 七、自己跑

被审的测试文件和直接相关的已有测试单独连跑 3 次（深度验证 5 次），看是否稳定。全量只在派单写明时跑。

## 八、输出

报告写到派单指定的路径：
- 第一行：执行方和档位
- 验证层级：阶段验证 / 深度验证（触发条件：…） / 全量验证
- 已执行的检查：实际跑过的命令或测试范围，附结果和退出码
- 未执行的检查：按层级跳过的、留待全量验证的、需要真机或现网确认的。没有实际运行的检查不得写成已通过。
- 结论：可合并 / 修复后可合并 / 不可合并
- 阻断问题（0～N 条，编号 R-<批次>-<方面>-<序号>）
- 应修问题（最多 5 条，按严重度排序）
- 待核对（需要真机、现网或用户确认的事项，最多 3 条）

没有发现问题时，直接写「未发现阻断或应修问题，可合并」，不要为了凑数列出低价值意见。

最终回复只放：结论、阻断和应修问题（每条一行）、报告路径。

## 九、复核者（修复之后）

只核对主控给的修复清单和对应的反例测试，不重审整批，不对清单以外的代码提新问题（看到明显的阻断问题可以记一行，标「清单外」）。报告开头同样写验证层级（沿用被复核批次的）、已执行和未执行的检查。每条写：已修 / 未修 / 修了但引入新问题，附证据。
